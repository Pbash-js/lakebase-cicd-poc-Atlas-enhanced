# Lakebase CI/CD — Atlas Community Edition migrator (reference POC)

Drop-in migration pipeline for Lakebase Postgres. Atlas Community Edition
(Apache-2.0, no login, no data leaves the workspace) plans migrations from a
single declarative SQL schema and applies them with an exactly-once ledger.
GitHub Actions runs CI on every PR and CD to production on merge.

```
SOURCE (Git)                DEPLOYMENT (Atlas CE + DABs)         DATABASE (Lakebase)
db/schema/schema.sql   ->   gen_migration.sh  (plan, per PR)  ->  pr-<n> branch (rehearsal)
db/objects/ (code SQL) ->   apply_migrations_atlas.sh         ->  production (on merge)
                            deploy_db.sh (entrypoint)
```

## What each file does

| Path | Role |
| --- | --- |
| `db/schema/schema.sql` | Desired state: one declarative SQL file (tables, columns, indexes, FKs, enums). The single source of truth for structural schema. |
| `db/migrations/` | Versioned SQL **generated by Atlas**, never hand-edited. Enforced by the CI immutability gate: a PR may only ADD files here. |
| `db/migrations/atlas.sum` | Atlas integrity file. Editing any migration requires changing it too, so tampering is always visible in the PR diff. |
| `db/objects/` | Code objects (functions, procedures, views, triggers), one file per object, replayed idempotently in layer order. These are Pro-only in Atlas, so they stay hand-owned here. |
| `db/tests/` | pytest suite run against the PR branch after deploy. |
| `scripts/gen_migration.sh` | The one command for schema changes: creates a dev branch, builds a throwaway scratch DB from `template0`, runs `atlas migrate diff`, writes the migration. |
| `scripts/apply_migrations_atlas.sh` | Applies pending migrations via `atlas migrate apply`. Ledger: `atlas_schema_revisions` (Atlas-managed: exactly-once, per-revision checksums, advisory lock between writers). First run against a pre-Atlas DB sets the baseline. |
| `scripts/deploy_db.sh` | Deploy entrypoint: mints a 1-hour OAuth credential, then Atlas apply -> objects -> tests. Production is reachable only inside GitHub Actions CD. |
| `.github/workflows/pr-validation.yml` | Per-PR checks (see "What CI fails on" below). |
| `.github/workflows/cd-promotion.yml` | On merge to main: DAB deploy + Atlas apply to production, serialized, never cancelled. |
| `.github/workflows/cleanup-orphans.yml` | GC for leftover ephemeral branches. |

## Developer loop

### Setup (once)
```
git clone https://github.com/Pbash-js/lakebase-cicd-poc-Atlas-enhanced.git
cd lakebase-cicd-poc-Atlas-enhanced
curl -sSf https://atlasgo.sh | sh -s -- --community   # Atlas CE binary
databricks auth login --profile free-edition
```

### Schema change (tables, columns, indexes, enums)
1. Edit `db/schema/schema.sql`.
2. Run `./scripts/gen_migration.sh` — one interactive command: it names a dev
   branch (`dev-<user>-<date>`, created off production with a 1-day TTL if
   missing), builds the scratch DB, and writes the generated migration.
3. Commit both the schema edit and the generated file, push, open a PR.

### Code-object change (functions, procedures, views, triggers)
1. Edit the object file in `db/objects/<layer>/` (CREATE OR REPLACE).
2. Commit, push, open a PR. No generation step.

### What CI does on your PR
1. Provisions or reuses the `pr-<n>` Lakebase branch and waits for its
   endpoint (an `IDLE` endpoint is fine: it wakes on first connection).
2. Plan check: regenerates the migration from `schema.sql` and compares.
3. Deploys migrations + objects to the PR branch, then runs the tests.

### What CD does on merge
1. Deploys the DAB (branch + endpoint adoption).
2. `atlas migrate apply` to production: only the migrations production lacks,
   exactly-once and tamper-checked. Then objects replay and tests.

## What CI fails on (exactly)

| Gate | Fails when |
| --- | --- |
| Infra-file integrity | PR touches `.github/`, `scripts/` or `databricks.yml` without the `infra-approved` label |
| Migration immutability | PR edits or deletes an existing file in `db/migrations/` (adding new ones is the only allowed change) |
| Atlas plan check | `db/schema/schema.sql` and `db/migrations/` disagree. CI posts the exact planned SQL as a PR comment; regenerate locally and commit it |
| Atlas apply | `atlas.sum` mismatch (tampered history), or a migration fails against the PR branch |
| Tests | pytest suite fails against the PR branch |
