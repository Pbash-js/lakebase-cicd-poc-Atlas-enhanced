# Lakebase CI/CD — Atlas Community Edition (enhanced POC)

Enhanced variant of the Lakebase CI/CD POC: Atlas CE (Apache-2.0) plans and
applies versioned migrations; everything else (branching, DABs, objects
replay, gates, CD) is unchanged from the POC.

## Repo layout
- `db/schema/schema.sql` — **desired state**: single declarative SQL file (tables, columns, indexes, constraints, enum). The Atlas source of truth for structural schema.
- `db/migrations/` — versioned SQL **generated by Atlas CE** (`atlas migrate diff` from the desired state). Never hand-edit an applied file: edit `db/schema/schema.sql`, regenerate.
- `db/migrations/atlas.sum` — Atlas integrity file (directory + per-file checksums). Replaces the SHA-256 drift gate; merge conflicts are deliberate.
- `db/objects/` — stateless code objects (functions, procedures, views, triggers), replayed idempotently (CREATE OR REPLACE) in layer order. Views/functions/triggers are Pro-only in Atlas, so they stay here.
- `db/tests/` — pytest suite run against the PR branch.
- `scripts/gen_migration.sh` — wraps `atlas migrate diff` against a scratch database (created from `template0`) inside the target branch. `--check` fails the PR if committed migrations do not converge to the desired state.
- `scripts/apply_migrations_atlas.sh` — Atlas-native apply engine. Ledger = `atlas_schema_revisions` (its own schema), maintained by Atlas: exactly-once, per-revision checksums, advisory lock between writers. First run against a pre-Atlas DB sets the baseline (documented adoption path).
- `scripts/deploy_db.sh` — deploy entrypoint: mint 60-min OAuth credential -> Atlas apply -> objects -> rbac -> tests. Prod guard unchanged (production only inside GitHub Actions CD).
- `.github/workflows/` — pr-validation.yml (ephemeral TTL branch per PR, Atlas plan check + deploy), cd-promotion.yml (Atlas apply to production on merge), cleanup-orphans.yml.

## Developer loop (schema change)
1. Edit `db/schema/schema.sql`.
2. Regenerate: `TARGET_BRANCH=<your-branch> ATLAS_BIN=<path-to-atlas> ./scripts/gen_migration.sh <name>`
3. Review the generated file in `db/migrations/`, commit both it and the schema edit, open the PR.
4. CI fails loudly if the committed migrations don't converge to the desired state.

## Local setup
```
databricks auth login --profile free-edition
curl -sSf https://atlasgo.sh | sh -s -- --community   # Atlas CE binary
./scripts/deploy_db.sh                                # interactive: targets a dev branch
pytest db/tests -q
```

## GitHub secrets required (Settings -> Secrets and variables -> Actions)
| Secret | Example |
| --- | --- |
| DATABRICKS_HOST | https://dbc-xxxxxxxx.cloud.databricks.com |
| DATABRICKS_TOKEN | PAT (POC) or SP OAuth secret |
| LAKEBASE_PROJECT | core-app-db |
| DATABRICKS_PG_USER | your Lakebase Postgres role (user email or SP client id) |

## Atlas CE boundary (what stays ours)
Pro-only in Atlas (lint, drift detection, views/functions/triggers, Registry,
GitHub Action) is covered by: `db/objects` replay, the exactly-once ledger +
`atlas.sum`, and our own plan-check CI step. No Pro licensing, no data
leaves the workspace.
